# Explicit native and file-claim preparation

This is source for a future authorized installation. No activation, confirmation, tests, build or deployment was performed during its implementation. Ordinary setup continues to use the standard connection and does not invoke the new command.

The adapter supports `--native-activation <preview|confirm|apply|recover> <codex|claude> <promotion|enable|disable> --connection <absolute-private-connection-folder> --profile <absolute-client-profile>`. Native promotion is Codex-only; file-claim enable/disable supports the two providers. The read-only Repair check also includes an activation preview.

Start with `preview`. It describes the exact owned files and changes or returns a specific refusal. A preview does not enable hooks, change transport, issue permission evidence or approve trust. The supported source path requires an enrolled connection and its exact current owned launcher, profile, helper and candidate. Unsupported local/development connections, modified definitions, disabled hooks, stale ownership or unverifiable inputs are refused rather than adopted.

`confirm` is an optional interactive operator attestation after the actual installed-client permission checks have been performed with authorization. It refuses redirected input/output, displays the exact scope and outcomes to be checked, and requires the operator's exact confirmation. The resulting private credential-authenticated receipt lasts five minutes and is tied to that candidate, helper, connection and profile. It is explicitly operator confirmation, not a provider-signed statement or proof inferred from hook stdin. It never writes Codex trust approval. A candidate, a startup receipt, a successful tool listing, arbitrary JSON and a command-line success flag cannot substitute for this step.

`apply` performs only the explicit selected plan. It replans and pins the settings and ownership dependencies, checks snapshots and current evidence, and records bounded private before/after images before writing. Promotion changes the owned native handlers and launcher together. File-claim changes prepare the owned PRE, POST and failure handlers with explicit profile binding. Edited and unrelated handlers are retained. Preview and apply refuse recognized historical handlers when exact safe reversal is unavailable; they do not report successful disable while an older guard remains.

`recover` is for a retained owned transaction journal. Recovery restores only the exact known before/after states. A partial write or later external edit retains the journal for manual resolution rather than overwriting that change. Apply/recovery is Windows-only and requires existing ordinary target files; it does not traverse settings links or create a missing profile implicitly.

After an authorized build, tests and deployment, installed-client permission behavior, both hook event paths, replacement and reversal, transaction interruption and real idle wake must be checked separately. Real wake evidence remains an actual new turn, correlated reply and acknowledgement; a receipt or queue exit alone is insufficient. None of those runtime outcomes is claimed by this source milestone.
