# File claim consumer checkpoint

The existing `claim_acquire`, `claim_renew` and `claim_release` tools accept `filePath` instead of `resourceId` for a native chat with a protected checkout. This is a canonical ASCII relative path (at most 512 characters), proved by the adapter. The hub freshly resolves `VerifiedNativeFileScope`, derives the opaque `file-v1:` key from repository, authenticated machine, canonical checkout and case-folded relative path, and resolves the same scope again after the lock call. No administrator resource registration is required. Generic resource claims and aliases cannot enter the reserved file namespace.

`claim_acquire` with `filePath` and positive `confirmGeneration` is a fresh read, not an acquire or renewal. It checks this holder, the exact generation, no unresolved action blocker, and at least fifteen seconds of remaining lease. Native dispatch does not cache or replay this confirmation. The edit guard has a ten-second budget and reconfirms the whole target set, preserving a remaining interval rather than authorizing from an old receipt. All ordinary session authentication and dispatch controls still apply.

The adapter uses the existing private native binding and generation-fenced `NativeJoin.CallAsync`. Its ledger is partitioned by repository/session/generation/checkout under the binding's private folder; it stores stable operation identities and uncertain outcomes, never tokens or file content. A lost acquire or compensation response cannot authorize an edit. Physical checkout, path containment, case semantics, reparse points and hard links are checked at use. Patch moves include both paths. Successful checks abstain so the client's own permission gate still decides.

The pre-edit handler is opt-in with `COCERN_FILE_CLAIMS=true` and supports Claude Edit/Write/MultiEdit and Codex apply_patch-shaped hook events. No hook matcher, client setting, native activation or live enrollment is installed or changed by this checkpoint. Unsupported event shapes and uncertain identity fail closed when the handler is enabled. Provider event delivery and block behavior still need the approved real-client acceptance window.

This checkpoint does not yet implement dirty-file activity renewal or commit/discard cleanup. The existing bounded lease remains the fallback; this is not the completed Part 6 lifecycle. Source review and the single called pre-deploy verification are still required. No test or build run was performed for this checkpoint; no runtime success is claimed.
