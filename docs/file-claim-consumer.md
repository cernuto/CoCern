# File claim consumer checkpoint

The existing `claim_acquire`, `claim_renew` and `claim_release` tools accept `filePath` instead of `resourceId` for a native chat with a protected checkout. This is a canonical ASCII relative path (at most 512 characters), proved by the adapter. The hub freshly resolves `VerifiedNativeFileScope`, derives the opaque `file-v1:` key from repository, authenticated machine, canonical checkout and case-folded relative path, and resolves the same scope again after the lock call. No administrator resource registration is required. Generic resource claims and aliases cannot enter the reserved file namespace.

`claim_acquire` with `filePath` and positive `confirmGeneration` is a fresh read, not an acquire or renewal. It checks this holder, the exact generation, no unresolved action blocker, and at least fifteen seconds of remaining lease. Native dispatch does not cache or replay this confirmation. The edit guard has a ten-second budget and reconfirms the whole target set, preserving a remaining interval rather than authorizing from an old receipt. All ordinary session authentication and dispatch controls still apply.

The adapter uses the existing private native binding and generation-fenced `NativeJoin.CallAsync`. Its ledger is partitioned by repository/session/generation/checkout under the binding's private folder; it stores stable operation identities and uncertain outcomes, never tokens or file content. A lost acquire or compensation response cannot authorize an edit. Physical checkout, path containment, case semantics, reparse points and hard links are checked at use. Patch moves include both paths. Successful checks abstain so the client's own permission gate still decides.

The pre-edit handler is opt-in with `COCERN_FILE_CLAIMS=true` and supports Claude Edit/Write/MultiEdit and Codex apply_patch-shaped hook events. No hook matcher, client setting, native activation or live enrollment is installed or changed by this checkpoint. Unsupported event shapes and uncertain identity fail closed when the handler is enabled. Provider event delivery and block behavior still need the approved real-client acceptance window.

The separate ledger-retirement follow-up adds `Snapshot()` (null on unavailable or lost storage) and `RetireReleased(intentId)`. Retirement requires an explicitly released intent and a confirmed positive generation with released outcome on every target. It removes full receipts atomically with an 8 KiB monotonic refusal filter for retired IDs. A retired retry cannot create new requests after restart. Hash collisions or eventual saturation only refuse new edits; existing active receipts still update. The filter never resets within a native generation. A durable initialization fence and serialization lock live in the parent native binding folder, outside the ledger directory; missing initialized files or directories fail closed. Schema 1 ledgers migrate without dropping receipts; malformed schema 2 filters also fail closed. One source-only test covers this replay/data-loss boundary, including whole-directory loss; it has not run.

The adapter lifecycle is `--file-claim-hook <codex|claude> --connection <folder>`, a PostToolUse handler opt-in behind the same `COCERN_FILE_CLAIMS`. Nothing installs it and no native activation changes. It is separate from `--native-hook` because that entry fails closed on input it cannot read and tool results can be large; this one prints nothing and always exits 0. A subagent event records nothing. Reads, searches and CoCern tools leave at once, so `check_inbox` and status calls never act as a heartbeat. A shell command costs one small file read unless this chat holds a claim and either a renewal is due or the command names git.

The PRE hook saves a sidecar row beside the ledger for each target of an abstained edit: `intentId`, `relativePath`, `beforeFingerprint` (SHA-256 or absent, never content), and later `afterFingerprint` and `observedActivity`. The POST correlates only by the exact `tool_use_id` and that saved row inside the generation's private partition, so nothing in the payload can assert ownership. An own change is recorded only after a successful result in a known form, changed content, and Git reporting the file dirty.

`claim_renew {filePath, generation, leaseSeconds: 120}` goes out only for the guard's own grant, with an own change on record, the file dirty per Git and still holding that change's fingerprint, and at most sixty seconds of lease left by the last known value. A reply-lost renewal replays its reserved invocation.

Commit or discard is decided by fresh per-file Git state alone. The shell command text only prompts a look, so a commit made in Visual Studio is seen at the next edit or git command. Clean means `git status` reports nothing for the file against HEAD or the index, and `git ls-files -v` shows it is neither assume-unchanged nor skip-worktree. Ignored files, nested repositories, hidden states and Git failures are unknown. A stash counts as a discard. `claim_release {filePath, generation}` uses the grant's acquire RequestId plus `-clean-release`. It is withheld while a sibling intent on the same claim is open or any receipt for the path is unsettled, and a pre-owned grant is never renewed or released here. An unanswered release stays release-unknown, renews nothing, and replays only while Git still says clean; `UnresolvedAction` stays recorded. Only a reply saying released, a definite `StaleClaim`, a newer confirmed generation in this ledger, or a fresh read showing the generation over marks receipts released and retires them. A settled pre-owned duplicate is retired early, since it made no grant and would otherwise fill the 128-intent ledger.

A PRE and a clean release cannot interleave. One cross-process gate beside the ledger directory covers PRE's acquire, confirmation and published attempt, and the sweep's fresh read of attempts, Git state and release answer, so either the sweep sees the attempt or the release finished before the guard confirmed. PRE waits at most four seconds and then refuses the edit; a sweep waits at most two and then skips that release. Lock order is sweep gate, decision gate, then the short ledger, sidecar and binding gates. A release whose reply was lost may still be queued at the hub, and a read still showing this holder proves only that it has not applied yet, so a PRE confirming that same generation refuses with no time limit. Only the hub's answer to a replay of that invocation (released, or stale) or a newer generation ends this; a blocker refusal of a replay does not, because the hub does not store it. A read answering not held ends it only when it shows a different generation or a lease clearly past; an answer missing or garbling either field changes nothing. Nothing renews the claim meanwhile and an acquire on a held claim does not extend it, so it lapses within the lease and the next edit takes a newer generation, which that release can't touch.

Limits, all of which end in lapse rather than a false release: the lease is 120 seconds, so a tool or thinking gap longer than that drops protection until the next edit re-acquires; a formatter or other shell rewrite of a claimed file stops renewal until the next own edit. Each renewal also spends one of the binding's 4096 mutation-fence slots, and acquires, releases and messages already do, with no pruning in this checkpoint. Renewing about once a minute per dirty file, continuous renewal alone uses them up in roughly 68 hours for one file, 64 minutes for 64 files or 32 minutes for 128. Running out refuses safely but stops renewals and edits until the binding is replaced, so activating this natively needs a bounded renewal or retention design first; old fences must not simply be deleted, because they stop replays. Client event shapes are assumed from documentation: `PostToolUse` and `PostToolUseFailure` carrying the PRE's `tool_use_id`; Claude's `tool_response.filePath`; Codex apply_patch answering a `Success` string, or `success` true or exit code 0. Other forms record no evidence. The pre-permission hook also cannot by itself revalidate after a delayed client permission decision. Source review and the single called pre-deploy verification are still required. No test or build run was performed for this checkpoint; no runtime success is claimed.
