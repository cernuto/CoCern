# Node Self-Update Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A joined node receives a verified build from its own hub and activates it between wakes; a failed update leaves its previous node working without local repair.

**Architecture:** Extend the existing authenticated discovery announcement with an optional release descriptor and reuse the hub's ZIP cache and pinned HTTP transport. Keep a stable supervisor in the existing adapter executable, run immutable node versions as children, and use a private atomic journal plus the existing node singleton and wake database for activation and rollback. No new service, message channel, role, manager power or user setting.

**Tech Stack:** C#/.NET 10, existing ASP.NET Core discovery endpoints, System.IO.Compression, SHA-256, owner-only files, existing Windows sign-in registration and process launch.

**Spec:** [Approved auto-connect design](../specs/2026-11-03-auto-connect-design.md), part 9 “Nodes update themselves”, acceptance gate 8; [feature acceptance cases](../../audits/2026-11-03-feature-build-acceptance.md), 9.2–9.3 and real native-client/two-PC coverage.

## Review Focus

- Publication changes between announcement and download: reject mismatched bytes and keep the old node; Task 1/2 tests.
- ZIP path aliases, links or decompression bombs: no extraction outside a fresh private staging root and no execution; Task 2 tests.
- A wake is reserved, dispatching or uncertain at activation: preserve its durable state and never replay it to force success; Task 4 tests.
- Child, supervisor or PC dies during each journal transition: restart deterministically selects committed old/new state with one node owner; Task 3/4 tests.
- A newer node is reported as a newer installed MCP client, or an old node lacks bootstrap: report separate identities and a real prerequisite; Task 5/6 tests.

### Task 1: Publish one authenticated, immutable release descriptor

**Interfaces:** In `CoCern.Contracts`, define `NodeFramework(string Name, string Version)`, `NodePackageMetadata(int Schema, string ProductVersion, string TargetFramework, string Rid, bool SelfContained, NodeFramework[] Frameworks, int SupervisorProtocol)`, `NodeRelease(int Schema, string ReleaseId, NodePackageMetadata Package, long ZipBytes, string ZipSha256, string AdapterDllSha256)`, and `NodeImage(string ContentId, NodePackageMetadata Package, string AdapterDllSha256, string? ReleaseId)`. NodeImage belongs to this shared contract file so Task 2 can compile before Task 3; only bootstrap has null ReleaseId. Both schemas and supervisor protocol are 1. `ReleaseId == ZipSha256`, uppercase 64-digit hexadecimal: identity of exact ZIP bytes, not chronology. Add optional `nodeRelease` to successful machine announce reply JSON; old clients ignore it.

**Producer/lease contract:** In `JoinEndpoints.cs`, introduce `sealed class AdapterReleaseLease : IAsyncDisposable` with get-only `NodeRelease Release`, get-only readable `Stream Content`, and idempotent `ValueTask DisposeAsync()`. Add `Task<AdapterReleaseLease?> AdapterZipCache.ReleaseAsync(string adapterFolder, CancellationToken ct)` and `Task<AdapterReleaseLease?> AdapterZipCache.OpenReleaseAsync(string releaseId, CancellationToken ct)`. Null means unavailable/invalid package. Each lease owns its opened verified stream and cache-pruning reference; disposal closes/releases both. Announcement uses `await using` and copies only `lease.Release` into JSON. ZIP response owns the lease until response completion/abort; dispose on every path. A retained lease prevents pruning its open content. Never leave a stream lifetime to a fresh worker's interpretation.

**Authoritative package metadata:** Add `NodePackageMetadataReader.Read(string folder) -> NodePackageMetadata?` in the adapter, reusable by the host (which already references the adapter). Producer reads only that folder's `CoCern.Adapter.dll` PE assembly metadata, `CoCern.Adapter.deps.json` (`runtimeTarget.name`) and `CoCern.Adapter.runtimeconfig.json` (`runtimeOptions.tfm`, `framework`/`frameworks` or `includedFrameworks`). ProductVersion comes from DLL informational version; supervisor protocol comes from assembly metadata key `CoCernNodeSupervisorProtocol`, generated by `<AssemblyMetadata Include="CoCernNodeSupervisorProtocol" Value="1" />` in the adapter project. Missing protocol means pre-updater/incompatible, not protocol 1 by guess. A `/win-x64` or `/win-arm64` suffix on the deps runtime target supplies RID; no suffix is `any` only for a framework-dependent AnyCPU assembly. Self-contained requires `includedFrameworks`, no external `framework(s)`, an explicit supported Windows RID, `CoCern.Adapter.exe`, `coreclr.dll` and `hostfxr.dll`; their PE machine types must match the RID. Framework-dependent requires external framework declarations, no includedFrameworks, and the assembly architecture must agree with explicit RID or AnyCPU. Reject inconsistent/unknown metadata instead of inferring hosting RID. These files are existing .NET build/publish outputs; no new metadata catalog or handwritten sidecar. Host derives this record before ZIP creation, then rechecks folder stamp/DLL digest before issuing the lease; client rederives and requires field-by-field equality after verified extraction (framework name/version tuples compared as sorted ordinal sequences, not record-array reference equality).
