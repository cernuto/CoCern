# Chat decisions implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Paul can approve a bounded goal, or answer a Standing proposal once in the chat he is using, and see or undo the resulting authority on the dashboard.

**Architecture:** A session-verified recording operation commits to the existing task-board aggregate. The board serializes presentation of each Standing proposal. Active lines, grants and Standing history carry the answer and its provenance. During direct human interaction the chat requests a question on an ordinary model-visible tool call.

**Tech stack:** Existing .NET 10, Orleans board/session grains, SQLite state, MCP adapter, Blazor dashboard and xUnit.

**Spec:** [Approved auto-connect design](../specs/2026-11-03-auto-connect-design.md), part 7, safeguards from 9–11 and acceptance gate 7. Supporting acceptance cases: 9.5, 9.6 and the authority boundaries in 10.2/11.5. This plan does not implement the capability runtime, manager powers or node updater.

## Global constraints

- “A goal is an existing task (or workflow) with a grant attached, not a new kind of record.” Use the existing repository/board key, Standing grant expiry, request replay, attention outbox and dashboard removal. No additional approval store, message transport, human-verification service, role, profile, environment variable or user switch.
- The approved design says “the hub therefore trusts the recording chat's word that Paul approved”. Only the current direct human answer counts. The hub checks the recording session, target, scope, expiry, quotation and concurrency. A noncompliant chat could fabricate a quotation. Paul accepted that risk for a single-user hub. A peer or manager message, a previous quote, a label and administrator tool visibility confer no human authority.
- The goal permits routine work toward its stated purpose among its members: sharing repository findings, handing off bounded tasks, editing, testing, claiming, committing on a working branch, replying and waking. No main push/merge, destructive action, out-of-repository action, capability upgrade, override of client prompts or recovery of another session's unsettled actions. Goal ownership is separate from a task claim, a role or manager appointment.
- Preserve unhooked clients, raw REST fields, administrator-only `standing_put`, valid legacy Standing grants and sign-in/removal. New protocol support is additive. No synthetically attested fixture records, native chats, dashboard sessions or customer data from the shared hub may be used to grant live authority.
- Execute against the feature worktree, sequentially after other owners release overlapping contract/domain files. Use both Roslyn CodeLens (load its skill and verify the feature solution) and Visual Studio MCP (verify the primary solution read-only). Never build into the running app's outputs. No Git attribution; Manager integrates each reviewed task.

## Review focus

1. Two human-active chats race for the same question; only the eligible winner may record the answer, and no watcher, wake or transport retry creates another question (tasks 1–2).
2. A matching quote delivered by a peer, a queue, a past turn or the chat itself results in no recording call. Public protocol fixtures cannot demonstrate this client behavior (tasks 2 and 4).
3. A stale replacement proposal, expiry during deliberation, oversized escaped answer, forged caller metadata, or replay after removal must never silently broaden authority (tasks 2–3).
4. A named chat forks, reconnects, loses its session, changes labels or arrives after a repository-wide goal starts. Match verified participants, isolate repositories and preserve action recovery (task 3).
5. A previously queued proposal or long-idle manager still cannot wake solely for proposals; other actionable mail must wake promptly. An unavailable presenter leaves the proposal visible/removable with no approval implied (tasks 1 and 4).

## Execution order and current interfaces

Tasks 1 and 2 can use the owned session verified by `CallGuard.VerifyAsync` today. `ReplyAddOns.IsBoundary` already identifies `task_update`, `action_report`, `task_claim` and `check_inbox`. `CallControls.Take` distinguishes model-visible requests, attention opt-out and waits. Its `backgroundCall` report affects telemetry only. The existing Claude prompt hook reads `session_id` and may cache a one-line status. Session verification and the recording chat's attestation are sufficient to ship the bounded Standing operation.

Task 3 depends separately on design part 1 providing stable participant identity, a current verified session for a returning participant, and unique peer resolution for named membership. This permits durable goal owner/member continuity across replacements, keeps forks distinct and preserves explicit action recovery. Parts 1–3 can later place the same presentation request on an existing automatic native delivery call during direct interaction. The two-client release gate measures whether that integration or shared chat guidance actually delivers questions without Paul asking for them.
