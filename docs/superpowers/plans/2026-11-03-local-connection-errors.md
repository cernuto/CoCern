# Local connection discovery and errors implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Connect local chats to the hub's configured loopback HTTP listener and tell a caller whether the hub could not be reached, its identity changed, or its sign-in was rejected.

**Architecture:** Reuse the existing REST forwarder, certificate callback, and local endpoint record. Extend the non-secret endpoint metadata without changing its TLS identity fields. Dashboard Connect selects from running server addresses; CLI Connect selects from the hub's record beside the existing credential. Neither discovers a remote address by probing.

**Tech stack:** .NET 10, System.Net.Http, ASP.NET Core Kestrel, System.Text.Json, xUnit.

**Spec:** [Auto-connect design, part 8 and acceptance gate 6](../specs/2026-11-03-auto-connect-design.md). This slice delivers error classification and local endpoint selection. It does not claim full gate 6: bootstrap, deliberate acceptance of a replacement identity, and the real two-PC exercise are separate.

## Global constraints

- Traffic between PCs stays encrypted, the hub's identity stays checked and every caller still has to prove who it is. Same-PC HTTP accepts the design's local port-squatting tradeoff; nothing falls back from remote TLS to plaintext after failure.
- Local discovery never outputs a wildcard, LAN, credentials, query, fragment, non-root path, or port zero. Return a numeric loopback origin; normalize localhost to 127.0.0.1, retaining the port. Retain an explicitly bound IPv6 loopback rather than substituting IPv4.
- Use the feature worktree and verify both Roslyn CodeLens and Visual Studio MCP before C# work. Use Roslyn for semantic lookups and diagnostics. The primary VS solution stays running and read-only. Use temporary profiles, endpoints, synthetic credentials and isolated test outputs; no live config, trust edits, or deployment.
- Task 2 starts **after** the certificate-recovery owner releases `HubNetwork.cs` and its tests. Preserve the identity guard, recovery metadata, and legacy pinned client compatibility. The other team's hook files are out of scope.

## Review focus

1. A different presented certificate and an ordinary outage on the same client must not share a failure flag (Task 1).
2. Unauthorized and forbidden mean different things; an untrusted response body or exception must not reach the user (Task 1).
3. Custom ports and IPv6 must work without turning wildcard or non-loopback addresses into local destinations (Task 2).
4. An upgraded local connection must not repoint a remote, node, or other hub's entry, even if credentials or fingerprints coincide (Task 2).
5. HTTP-only startup must not leave empty TLS evidence that blocks a future first TLS identity. Old binaries/records must still work (Task 2).

## Follow-up evidence: removing normal credential configuration

- **Current local source of truth:** `RelayAuthentication.LoadClients/CreateTokenFile` already creates and reads a random owner-only file. `Start-CoCern.ps1` and the Visual Studio profile select `data/local-client-token`; the script currently creates it separately and prints the path. `ConnectCommand.FindTokenFile` already locates that file above the **adapter installation**, independent of the chat's checkout. The supported published layout is `artifacts/adapter` under the install root (README). `DashboardConnect.TokenFile` can identify a deliberately non-default admin file. `LocalWakeConnection.Create` currently needs the resolved private file path to verify the credential without copying it; removing an environment variable without supplying an internal resolved path would break local wake.
- **Smallest default-layout candidate:** For local entries created by Connect, bind local discovery to the adapter installation, let the adapter resolve the **same existing hub-owned file** and recorded endpoint internally, and pass its resolved path internally to local wake. No second credential, registry, public credential endpoint, or separate message path. Use a non-secret local-mode discriminator if needed so an empty-env joined worker never falls through into a local administrator credential. Keep explicit overrides and nonstandard/multi-hub layouts distinct; never search an arbitrary chat working directory, automatically escalate an existing worker, or use a discovered local secret with an arbitrary remote URL. Make the host the sole first-run writer and remove the script's secret-path output in that slice. This candidate relies on hub data outside a private package overlay and one coherent adapter/data installation, not arbitrary colocated files.
- **Remote already works differently:** `AdapterOptions.FromEnvironment/FromNode` and `NodeState.ReadEnrollment` discover the enrolled PC's credential and require its stored HTTPS pin. Node mode is never administrator. `NodeState.SaveCredential/CreatePrivateFile` writes a user-only Windows ACL or Unix 0600. Keep that precedence and ownership. `SetupEnvironment.Create` currently restricts the one-paste setup command to Windows; Linux **local credential discovery** does not imply Linux node auto-start/one-paste setup is implemented.
- **Platform evidence and gate:** Microsoft documents that virtualized packaged desktop apps can create private AppData overlays and open the package copy before the real path; full trust and AppContainer are distinct settings. [Packaged desktop app filesystem behavior](https://learn.microsoft.com/windows/msix/desktop/desktop-to-uwp-behind-the-scenes#file-system). [Known-folder flags](https://learn.microsoft.com/windows/win32/api/shlobj_core/ne-shlobj_core-known_folder_flag#constants) can return an unredirected *path*; that alone does not prove cross-package file access or eliminate an existing shadow. The repo's [wake audit](../../audits/2026-11-03-permanent-wake-tests.md) observed separate per-app caches. Before making the candidate the default, prove an unpackaged host and both packaged app-launched adapters can read the same synthetic, owner-only file from the documented external install tree. Repeat on Linux from an unrelated working directory and assert no credential/file path in either client's generated config or normal setup output. Test cross-install collision, changed/deleted file, joined-node precedence, local wake and non-default data location; retain explicit overrides there until an unambiguous same-user binding exists. Do not inventory users' real credentials or relax ACLs.
- **Separate trust-change work:** A mismatch is diagnostic only. A later plan must bind an explicit confirmation to the intended machine/hub and observed replacement identity, revalidate before persisting, and reject a second substitution. This slice never approves, stores or retries against a replacement identity.
