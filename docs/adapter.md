# Local stdio adapter

PkRelay.Adapter uses the official Model Context Protocol C# SDK and standard stdio transport. Configure the client to start the adapter executable, or use `dotnet` with the absolute path to a published `PkRelay.Adapter.dll`. In normal MCP mode, standard output carries MCP only and diagnostic messages use standard error. Normal MCP tool calls forward coordination requests and never execute local commands or control an IDE. The separate opt-in [local Codex wake mode](wake.md) can queue fixed inbox-check prompts for explicitly enrolled desktop chats.

Set `PKRELAY_URL` to the hub origin; the default is `http://127.0.0.1:5271`. Plain HTTP is allowed only for loopback. Other hosts require HTTPS with a valid certificate. URLs containing credentials, query strings, fragments, or a non-root path are rejected. HTTP redirects are rejected, including same-origin redirects, so the configured origin must be the final hub address.

Set `PKRELAY_TOKEN_FILE` to a file containing the client bearer token. Restrict that file to the intended account and keep it out of source control and shared artifacts. The bootstrap's ignored `data/local-client-token` file is for local development. A final newline is accepted. The file takes precedence over `PKRELAY_TOKEN`, which is the alternative for clients with protected environment configuration. Missing/unreadable credentials stop startup with a generic standard-error message. Tokens are never printed. The local client token does not configure remote ChatGPT OAuth or a Secure MCP Tunnel.

The default worker surface exposes `session_open`, `session_bind`, `worker_list`, `get_status`, `task_get`, `task_update`, `task_claim`, `claim_acquire`, `claim_renew`, `claim_release`, `action_begin`, `action_report`, `send_message`, `check_inbox`, `ack`, `context_get`, and `context_put`. Set `PKRELAY_ROLE=admin` to additionally advertise `control_request`; the hub still authorizes every operation. A local role setting grants no server permissions.

Tool definitions are re-sent in every model turn, so a chat that only exchanges messages should set `PKRELAY_PROFILE=chat`. The adapter then advertises and forwards only `session_open`, `send_message`, `check_inbox`, `ack` and `chat_directory`, which is about a quarter of the default surface's definition size; any other tool returns `unknown_tool`. Argument guidance shared by all tools is in the server instructions once, not in each tool's description. `send_message` accepts `ackMessageIds`, so a reply acknowledges the messages it handles in the same call. A chat that is mid-turn cannot be woken, so to wait for mail it should call `check_inbox` with `waitSeconds` (at most 50, under Codex's default 60-second MCP tool timeout) instead of polling: the adapter re-reads the inbox every 2 seconds inside that one call and returns as soon as a message arrives, while each poll would be a model call that re-reads the whole chat. `waitSeconds` is the adapter's own option and is never sent to the hub. Reads that a chat repeats on a schedule (`task_get`, `chat_directory`, `worker_list`, `get_status`, `context_get`) return an `etag` in their data; passing it back as `ifNoneMatch` returns only `{"unchanged":true,"etag":…}` while the data is the same, about 90 characters instead of the whole payload added to the chat's context again. `ifNoneMatch` is also never sent to the hub.

The hub keeps its own replies small in the same way. `task_update` and `action_report` acknowledge with the task ID, new version, change revision and update time, plus the actions that call reported; they no longer echo the whole task, which grew with every message. A whole-task `task_get` carries only the latest 20 messages, reports and attempts, with a `messagesTotal`, `reportsTotal` or `attemptHistoryTotal` when it trimmed one; read older entries with `section` and `cursor`. A private `send_message` with `supersede: true` replaces the sender's earlier unread superseding message to that recipient, so a periodic status request or heartbeat leaves one current entry in a busy chat's inbox instead of a pile. A private `send_message` with `wake: false` is for status and FYI notes that need no prompt action: it is stored and read with the recipient's next wake or `check_inbox`, but it never wakes the recipient itself. Every wake is a full model turn that re-reads the whole chat, so reserve waking messages for things the recipient should act on now.

Each MCP tool accepts the corresponding hub JSON object directly, including `repositoryId`, the session handle where required, `requestId` for mutations, and expected versions. The adapter posts that object to `/api/tools/{tool}` without accepting an arbitrary route or a caller identity. Results contain `ok`, `code`, `data` (the parsed hub `dataJson`), and `version`. Failed operations set MCP `isError`; recognized structured HTTP 400, 403, 404, 409 and 413 domain failures preserve their code, data and version when the published code agrees with the status. This includes actionable failures such as `RequestIdRequired`, `ResourceUnknown` and `VersionConflict`. Authentication middleware failures, malformed or unrecognized error bodies, and other transport failures return stable generic codes without raw response bodies or exception details. Caller cancellation reaches HTTP and is not converted to success. Adapter requests are limited to 64 KiB and hub replies to 128 KiB, including replies without a declared content length; the host imposes its stricter 32 KiB public request/reply envelope bound. Oversized results fail explicitly and should be retried with narrower pagination or context scope.

The compact forwarding schemas advertise every catalog-declared required operation field, session machine/label fields, message text and recipient/reply correlation, inbox pagination and acknowledgment IDs as well as task delta/workflow arguments. Only `repositoryId` is required by the forwarding schema; the hub still enforces private session handles, mutation request IDs and operation-specific requirements. `chat_directory` returns a bounded list with a truncation flag and does not support cursor pagination.

For claim renewal or release, supply either `resourceId` with its `generation`, or `taskId` with its `claimGeneration`. A task release also requires its current `expectedVersion`; a resource release does not. `claim_renew` accepts `leaseSeconds` and does not require a task version. These conditional fields are advertised even though neither identity alternative is globally required by the forwarding schema.

Open a fresh session for each chat. Use `task_claim` before direct IDE work, perform that work through the configured Roslyn CodeLens and Visual Studio MCP servers, and report useful milestones with `task_update`. Claims remain advisory. Retry an uncertain mutation with its original request identity after checking authoritative state; the adapter does not automatically replay mutations.

Inbox recovery is explicit: call `check_inbox`, handle each message, then call `ack` for the handled IDs. Reading an inbox does not acknowledge it, and acknowledgment does not complete a task. Task conversations survive replacement chats; another chat's private session inbox does not transfer.

Optional SignalR hints are enabled by `PKRELAY_SIGNALR=true`. After a successful `session_open`, the adapter watches only the session it just opened, authenticating `WatchSession(sessionId, sessionToken, repositoryId)`. Hints contain no message text or session token, are coalesced, and print a generic reminder to standard error. Reconnection reestablishes that watch. Connection failure does not undo a successful durable call. The optional client uses same-origin HTTP long polling and rejects redirects; it never forwards credentials to a redirected origin.

Standard-error hints do not wake a model or guarantee that a client will display them. Normal MCP mode advertises no Claude channel or ChatGPT event subscription. Explicit inbox checks remain authoritative after startup, reconnect, missed hints, and relay restart. The supported SDK owns protocol negotiation and cancellation; no custom MCP framing is implemented. To turn durable inbox changes into automatic local Codex follow-ups, enroll the exact chats in the separate `--wake` mode described in [wake.md](wake.md); ordinary stderr hints alone remain insufficient.
